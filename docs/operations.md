## NEWS: Pages CMSを採用

更新担当者がGitHubアカウントを使えることを確認済みのため、[Pages CMS](https://pagescms.org/)を採用しました。管理画面から記事と画像を編集するとGitHubに保存され、GitHub Actionsによってデモサイトへ反映されます。専用データベースやWordPressサーバーの保守は不要です。構成と日本語の編集項目は `.pages.yml` に準備済みです。

WordPressはプラグインや複雑な編集業務を維持したい場合、[microCMS](https://microcms.io/)はGitHubから独立した日本語の管理画面を重視する場合に候補になります。今回の静的な企業サイトとNEWSにはPages CMSが適しています。

### 初回のみ必要なアカウント操作

1. [Pages CMS](https://app.pagescms.org/)へGitHubでログインします。
2. GitHub Appの導入画面で、対象を `hirojessica/amenowa-renew` のみに限定して許可します。これはサイト公開とは別のアカウント操作です。
3. リポジトリ `amenowa-renew` とブランチ `main` を選びます。
4. 「お知らせ・ブログ」を開き、本番から移行した公開記事4件が表示されることを確認します。

2026年9月8日、hirojessicaアカウントで初回接続とCMSからの実更新を確認しました。接続範囲は `amenowa-renew` のみに限定しています。お知らせの作成・編集、事例と年表画像の登録、表示順変更、確認用データの削除までの記録は[Pages CMSの実更新確認](pages-cms-verification.md)をご覧ください。別の更新担当者を追加する場合は、その利用者のアクセス設定とログイン確認が必要です。

### 記事の追加

1. 「お知らせ・ブログ」で新規作成します。
2. タイトル、記事URL（半角小文字・数字・ハイフン）、公開日、カテゴリー、本文を入力します。
3. 必要に応じて一覧用の説明文、記事画像、画像の説明を設定します。
4. 「サイトに掲載する」をオンにして保存します。
5. GitHubの[Actions](https://github.com/hirojessica/amenowa-renew/actions)が成功した後、NEWS一覧と詳細ページを確認します。

公開日が未来の記事や掲載オフの記事はビルド成果物に含めません。ただし、このリポジトリ自体は公開されているため原稿ファイルは閲覧できます。未公開の機密情報は保存しないでください。時刻による自動公開は設定していません。未来日付の記事を掲載する際には、当日以降に保存し直すかActionsから再実行します。

公開後の記事URLは維持してください。2026-09-06に本番の公開記事4件を移行しました。移行一覧と添付ファイルの対応は [NEWS移行記録](news-migration.md) を参照してください。WordPressとの自動同期はありません。今後デモの記事を編集する際はPages CMSを使用します。

本文の画像・PDFは「メディア」に追加し、本文から参照できます。PDFは画像として挿入せず、`/uploads/ファイル名.pdf` へのリンクにしてください。デモのベースパスはビルド時に付与されます。

## お問い合わせ: FormSubmitを第一候補

指定の受信先は **info@amenowa.co.jp** です。公開デモは引き続き実送信しない設定です。2026年9月10日、利用者の依頼に基づいてローカルのlive環境から1回送信し、FormSubmitの受付画面を確認しました。ただしメール未着との回答があり、有効化・受信成功は未確認です。[受信テストの経過と本番時の確認](formsubmit-verification.md)を参照してください。

| 候補 | 向いている運用 | 今回の扱い |
| --- | --- | --- |
| [FormSubmit](https://formsubmit.co/documentation) | メールで受信するシンプルな問い合わせ窓口。既存KMN運用とそろえたい場合 | 第一候補。送信先、確認画面、完了ページへの遷移に対応する構成を準備 |
| [Formspree](https://formspree.io/) | 管理画面で投稿履歴や連携も扱いたい場合 | 代替候補。別途アカウントとフォームを作成し、プランを確認 |

メール中心の運用なら、今回はFormSubmitを継続して使う方針でよいと考えています。管理画面での履歴管理が必要になった時点でFormspreeを検討できます。

### FormSubmitの本番有効化手順

2026年9月8日、個人情報ページに管理責任者・保管期間・削除方法と、FormSubmit公式資料で確認した保存期間を反映しました。その後、ユーザーの承認により「利用しています」「原則として1年間保管します」等の公開用表現へ更新しました。実際の社内設定・外部サービスの保管場所等の確認は本番準備として残ります。[個人情報の掲載文と残る確認](privacy-operations.md)を参照してください。

1. `site/.env.example`を参考に、公開環境のビルド設定に `VITE_CONTACT_MODE=live` と `VITE_FORM_ENDPOINT=https://formsubmit.co/info@amenowa.co.jp` を設定します。ローカルの `.env.local` はGit対象外です。
2. 本番用の個人情報の取り扱いを確定し、フォームから参照できるようにします。
3. 管理者が自分のテスト情報で送信し、info@amenowa.co.jpに届くFormSubmitの有効化メールを確認します。最初の有効化前の送信を通常問い合わせとして扱わないでください。
4. 有効化後に案内されるランダム文字列の宛先URLへ `VITE_FORM_ENDPOINT` を置き換えると、HTMLに受信メールアドレスを直接記載せずに運用できます。この文字列はログやGitに保存せず、公開環境で設定します。ただし送信エンドポイント自体はブラウザーから見える公開値です。
5. 再ビルド後、受信、返信先、迷惑メール判定、入力内容、完了ページへの遷移を実際に確認します。

既定のreCAPTCHAを無効化せず、ハニーポットも用意しています。自動返信は現在設定していません。詳しくは[FormSubmitの説明](https://formsubmit.co/documentation)と[ヘルプ](https://formsubmit.co/help)をご確認ください。

**デモのActionsは `VITE_CONTACT_MODE: demo` に固定しています。** `.env.local` を変えるだけでは、このGitHub Pagesデモの送信は有効になりません。本番切り替え時に公開先とワークフローの設定を変更します。

Formspreeへ切り替える場合は発行された `https://formspree.io/f/…` のエンドポイントを設定し、リダイレクトやスパム対策はFormspree側でも設定します。FormSubmit専用の `_next` などがそのまま機能する前提では運用しません。
